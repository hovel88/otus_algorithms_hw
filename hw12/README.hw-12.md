## Подготовка

Для сборки исходников запустить `make`:

```bash

g++ -lstdc++fs -std=c++17 -O2 -Wall -I. -o hw12_hash main_hash.cpp
```

Мы будем рассматривать три варианта хэш-таблиц:

* использующую метод цепочек
* использующую открытую адресацию с линейным пробингом и ленивым удалением
* использующую открытую адресацию с квадратичным пробингом и ленивым удалением

Основными параметрами для теста этих алгоритмов будут выступать:

* количество коллизий:
  * для метода цепочек - когда при вставке цепочка для ключа уже не пуста
  * для открытой адресации - когда требуется более одной попытки
* фактор загрузки таблицы (load factor) - оценивается как отношение количества вставленных элементов к размеру таблицы
  * для метода цепочек делается рехэш таблицы по этому фактору, когда он больше 16.0 (средняя длина цепочки больше 16 элементов). по умолчанию в коде задано 3.0, но для теста увеличил, для наглядности
  * для открытой адресации делается рехэш таблицы по этому фактору, когда он больше 0.7. это значение жестко зашито в коде, не стал выносить
* время, затраченное на вставку
* время, затраченное на поиск
* время, затраченное на удаление

Для определенности, хотя я и постарался делать более общими классами, но тестирование будем проводить на парах ключ-значение формата (int, string).  
Для тестирования подготовим набор произвольных данных из 10000 элементов, этот набор будет использоваться для теста вставки.  
Также будет сформирован набор для теста поиска, он будет состоять из 10% ключей из набора для вставки, с добавлением некоторого количества ключей, которых заведомо не существует.  
А также будет подготовлен набор для теста удаления, он будет состоять из 50% ключей из набора для вставки.

## Решение

### Хэш-таблица, использующую метод цепочек

Реализован класс **ChainedHashTable** (исходники тут: `hw12/ChainedHashTable.h`).

### Хэш-таблица, использующую открытую адресацию (линейный пробинг)

Реализован класс **AddressingHashTable V1** (исходники тут: `hw12/AddressingHashTable.h`).

Функционал линейного (последовательного) пробинга находится в методе **sequential_probe_()**. Реализуется функция:

`h(k, i) = (hash(k) + i) % N`

Основное отличие от хэш-таблицы с методом цепочек, что при коллизии приходится искать один из ближайших подходящих слотов, хэш-индекс которого будет отличаться от хэш-индекса ключа. Таким образом мы с одной стороны занимаем чужие слоты при коллизиях, но с другой стороны - у нас не образуются длинные односвязные списки, которые приходится обходить линейно. Однако теперь нужно хранить состояние слота (пусто, занято, удалено) и применять "леновое" удаление.

### Хэш-таблица, использующую открытую адресацию (квадратичный пробинг)

Реализован класс **AddressingHashTable V2** (исходники тут: `hw12/AddressingHashTable.h`).

Функционал квадратичного пробинга находится в методе **quadratic_probe_()**. Реализуется функция:

`h(k, i) = (hash(k) + c1*i + c2*i^2) % N`

где `c1=1` и `c2=1`.

Основное отличие от хэш-таблицы с методом цепочек, что при коллизии приходится искать один из ближайших подходящих слотов, хэш-индекс которого будет отличаться от хэш-индекса ключа. Таким образом мы с одной стороны занимаем чужие слоты при коллизиях, но с другой стороны - у нас не образуются длинные односвязные списки, которые приходится обходить линейно. Однако теперь нужно хранить состояние слота (пусто, занято, удалено) и применять "леновое" удаление.

Наш тестовый набор из 10000 элементов состоял из рандомизированных значений. При этом было некоторое количество повторений. При повторениях ключа добавления нового элемента не происходит, а просто заменяется значение существующего. Это видно из того, что во все хэш-таблицы было вставлено 9498 элементов из 10000.

Когда производили поиск, мы использовали 10% из вставленных значений, а также добавили 100 значений, которых точно нет в таблице. Это видно из того, что было найдено 1000 элементов из 1100.

Для удаления мы использовали 50% из ключей, которые использовались для вставки. Тут также присутствовали повторения при рандомизированной генерации. Поэтому повторное удаление элемента с ключом, который был удален ранее - ни к чему не приводила и размер не уменьшался.

Также можем проконтролировать, корректность итогового количества элементов в хэш-таблицах после удаления: 9498 - 4864 = 4634.

Можно наблюдать, что алгоритм с открытой адресацией с квадратичным пробингом (**AddressingHashTable V2**) самый быстрый по всем операциям, а также имеет наименьшее количество коллизий.  
Думаю, что связано это с тем, что для цепочек мы проверяем, что хэш-индекс попал в не пустую цепочку, а в самой цепочке может содержаться несколько ячеек. Т.о. у нас меньшее количество цепочек, а значит чаще попадаем в одну и туже цепочку хэш-индексом.  
А для открытой индексации за коллизию я считал тот факт, когда хэш-индекс попадает на ранее уже занятый слот другим элементом, но из-за того что у нас бОльшее количество слотов (больше рехешей), то слоты распределяются лучше.

Также видно, что для **AddressingHashTable V2** коллизий меньше, чем для **AddressingHashTable V1** - потому что квадратичный пробинг лучше распределяет слоты, не допускает образования локальных кластеров.

Метод цепочек по времени операций самый медленный.

При этом для случая **ChainedHashTable (avg_load=16)** я специально разрешил использовать цепочки со средней длиной до 16 элементов, чтобы начал оказывать влияние последовательный перебор односвязного списка, вместо прямого доступа по индексу. В статистике видно, что в среднем получилось около 9.3 элемента на цепочку, в худшем случае все элементы приходится обходить. Однако видно, что алгоритм расширял таблицу меньшее количество раз (6 против 10), значит в таблице меньшее количество цепочек, а значит чаще происходят коллизии.

Для случая **ChainedHashTable (avg_load=2)** для сравнения я задал значение средней длины цепочки в 2 элемента. Как и ожидалось, цепочки у нас меньшего размера, поэтому придется сделать больше перестроений таблицы (9 против 6, почти столько же сколько и для открытой адресации). И это улучшило время работы на основные операции, потому что меньше приходится последовательно перебирать односвязные списки.

Вариант **ChainedHashTable (avg_load=2)** кажется что должен быть очень похожим на **AddressingHashTable V1**. Количество рехешей 9 против 10, количество элементов в одной ячейке таблицы 2 (load factor почти в 2 раза выше) против 1. Однако время в операциях отличается сильно. Наверное тут дело в лучшей локальности данных. В таблице с открытой индексацией элементы находятся последовательно в массиве, и наверное процессором лучше оптимизируются и кешируются. А в случае с цепочками такой локальности элементов нет.
